## Observed failure (real, from the user's machine and DB)
Publishing hostname `niga.online` (zone apex) failed at step "Create tunnel" with `Cloudflare network error: Missing tunnel ingress`, rollback failed with the same text. Persisted rows show `tunnel_created:true`, a real new tunnel id, `previous_config:null`, `dns_id:null`: the tunnel WAS created, then the very next call failed.

## Root cause (verified in code)
`CloudflareClient::get_ingress` does `GET /accounts/{a}/cfd_tunnel/{id}/configurations` and returns `CfError::Network("Missing tunnel ingress")` unless `result.config.ingress` is an array. A **brand-new remotely-managed tunnel has no configuration yet** (Cloudflare returns a null/empty `config`), so this normal state is turned into a failure. `deploy.rs` calls it (through `config()`) to snapshot `previous_config` right after creating the tunnel, so EVERY first publish fails. Rollback calls the same function, so cleanup fails identically and leaves the tunnel orphaned. Shape errors are also mislabeled as "network error".
Tunnel model: Hostify correctly uses **remotely managed** tunnels (`config_src:"cloudflare"`, ingress via the configurations API, connector run with `TUNNEL_TOKEN`). Keep exactly this model; do not add local config files / credentials files / `--config`.

## Required changes
1. **Config read.** `get_ingress` (rename if you like, keep a compat shim) returns `Result<Option<TunnelConfig>, CfError>`: `None` for a null/missing/`{}`/ingress-less config or a 404-style "no config" response; `Some` only when `ingress` is an array. Never an error for "not configured yet".
2. **Error classification.** Transport failures → `Network`. Non-2xx → `Api{status, code, message}` using the Cloudflare `errors[]` (map auth/permission/rate-limit/not-found distinctly). Unexpected JSON shape → a new `Unexpected(String)` variant (message says what was missing). Never call a shape problem a network error. Keep friendly user-facing strings.
3. **Sanitized API log.** Add an optional logger hook on the client (engine wires it to append to `logs/cloudflare.log`, rotated like the others). One line per request: timestamp, method, path (ids allowed), HTTP status, Cloudflare error codes + messages, duration. NEVER log the Authorization header, API token, tunnel token, `result` of `/token`, or request/response bodies that can contain secrets. Add a test that fabricates a token + tunnel token and asserts neither appears anywhere in the captured log.
4. **Deploy flow (remote-managed lifecycle):** create-or-reuse tunnel by stable name `hostify-<siteId>` (paginate, ignore deleted) → fetch tunnel token → if the tunnel was just created by THIS deployment, skip the snapshot (previous config = None); if reused, snapshot via the new `Option` read → PUT ingress `[{hostname, service:"http://127.0.0.1:<port>"}, …existing Hostify-owned entries for other sites on a reused tunnel…, {service:"http_status:404"}]` (final catch-all always 404) → DNS → start connector (`cloudflared tunnel --no-autoupdate run`, token via env only) → verify connector connected → verify public HTTPS.
5. **Rollback independent of config reads.** Track every created resource (already journaled: keep). Rollback must NOT depend on reading tunnel configuration to decide what to delete: for a tunnel with `tunnel_created && owner == this deployment`, stop our connector, then delete it; treat "tunnel not found" as success (idempotent). If deletion fails because the tunnel still has active connections, call `DELETE /accounts/{a}/cfd_tunnel/{id}/connections` (clean up connectors) and retry. Reused tunnel: restore the snapshotted config if one was taken (`None` snapshot ⇒ restore means PUT only the entries without our hostname, never delete a tunnel we didn't create). DNS: delete only our own tagged record; missing record = success. Never touch unrelated records/tunnels. Failed cleanup keeps a durable `rollback pending` marker; `recover_interrupted()` and engine startup retry it until it succeeds (existing retry test must keep passing).
6. **Recover the two real orphaned deployments.** Add a regression test whose fixture mirrors the persisted rows above (state `failed`, `tunnel_created:true`, `previous_config:null`, `dns_id:null`, incomplete rollback) and asserts that `recover_interrupted()` now deletes exactly that tunnel (mock Cloudflare, fake ids), is idempotent on a second run, and touches nothing else.
