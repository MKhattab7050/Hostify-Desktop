## A. Project inspection and import (`crates/hostify-core/src/project.rs`, new)
`inspect(path, "directory"|"zip") -> ProjectReport`, which never executes anything from the project. It reads from a folder or from inside a ZIP, using the same entry-name safety as `import.rs`, with a 2 MiB limit on each parsed file.

Report fields: `siteKind` (`static`, `node`, `php`, `unknown`), `framework` (`express`, `socket.io`, `next`, `fastify`, `koa`, or null, from `dependencies`), `name`, `engines` (the `engines.node` text), `recommendedRuntime` (a manifest Node version; newest pinned LTS satisfying a simple `engines.node`, otherwise the newest pinned LTS, plus a warning if it could not satisfy it), `scripts` (names and text of `build`, `start`), `lifecycleScripts` (root `preinstall`, `install`, `postinstall`, `prepare`, with text), `dependenciesWithInstallScripts` (names of packages with `hasInstallScript: true` in `package-lock.json`), `lockfile` (`package-lock`, `pnpm`, `yarn`, or null), `hasServerEntry`, `dotenvNames` (variable names from a root `.env`, never values), `usesDatabase` (hint from dependencies `mysql`, `mysql2`, `prisma`, `sequelize`, `knex`), `suggested` (an `AppConfig`, below), and `warnings`.

Classification: `package.json` with a `start` script, a `main`, a root `server.js`/`app.js`/`index.js`, or a `next` dependency is `node`. A root `index.php` or `composer.json` is `php`; report it, while task 13 implements hosting (`add_site` refuses it for now with a plain sentence). A root `index.html` with neither is `static`. A `package.json` with no way to start a server but an `index.html` or `dist/index.html` is `static` with a warning that it is served as files. Anything else is `unknown` with a sentence saying what was looked for. A pnpm or yarn lockfile is a warning: Hostify uses npm for now and ignores that lockfile.

`import_release(source, kind, site_dir) -> (SourceReport, release_id)` in `import.rs`: extract to `<site>/app/<release_id>/` through a staging directory, using the same checks and limits as `import`, sharing the code. Skip `node_modules` and `.git` at any depth, and a root `.env` (its values must not be left on disk by Hostify; the wizard imports them into the encrypted store through `import_env`). It never touches a running release. Provide `prune_app_releases(site_dir, keep: &[release_id])` keeping the active, the previous, and the newest.

## B. Configuration (`crates/hostify-core/src/app_config.rs`, new)
Stored in `websites.app_config_json`, camelCase, `#[serde(default)]` on every field:

`siteKind` is the column `kind`. `nodeVersion` is the column `runtime_version`. The JSON holds: `install` (`ci`, `install`, `none`), `buildScript` (a script name or null), `start` (tagged: `{type:"npmScript",name}` or `{type:"node",args:[...]}` where the first arg is a path relative to the working directory), `workingDir` (relative, default `.`), `healthPath` (default `/`), `restart` (`always`, `onFailure`, `never`, default `always`), `memoryLimitMb` (optional, 128 to 65536), `allowInstallScripts` (default false), `internalPort`, `activeRelease`, `previousRelease`, `pendingRelease`, `builtRelease`, and `trustedRelease` (a release id, see E).

Suggested defaults: `ci` with a package-lock, otherwise `install`. `buildScript` is `build` when present. Start: `{type:"npmScript",name:"start"}` when there is a start script; for Next.js `{type:"node",args:["node_modules/next/dist/bin/next","start","-p","{PORT}","-H","127.0.0.1"]}`; otherwise `node <main or server.js or app.js or index.js>`.

Validation, with a plain sentence for each refusal: `workingDir` and any path argument must be relative, with no `..`, no drive or UNC prefix, no NUL, and must stay inside the release after canonicalising (test with `..\`, `C:\`, `\\host\x`, and a junction). Script names must exist in `package.json` and are passed as a single argv entry. `healthPath` starts with `/` and has no spaces or control characters. Tokens are argv entries and are never concatenated into a command string. `{PORT}` is the only placeholder.

IPC: `inspect_project {path, kind}`. `add_site` gains optional `siteKind` (default `static`) and `config`; for `node` it uses `import_release`, allocates a separate internal port distinct from every site's public and internal port, stores the config, and does **not** start or install anything. `get_app_config {siteId}`, `set_app_config {siteId, config, nodeVersion}` returning `{restartRequired, rebuildRequired}`. `update_site_files` on a node site imports a new release and records `pendingRelease`; the running release keeps serving until a build succeeds and the new release starts and passes health.

## C. Install and build (`crates/hostify-engine/src/build.rs`, new)

## D. Process management (`supervisor.rs`, `windows.rs`)
**Process tree.** `Job` gains an optional memory limit (`JOB_OBJECT_LIMIT_JOB_MEMORY`), `terminate()`, `process_ids()`, and a `running()` check, using `QueryInformationJobObject`. Every app and build process gets its own Job Object nested inside the engine's (assign to the engine job first, while the process is still suspended, then to its own job; both with kill-on-close). Stop and crash handling always terminate the per-app job, so no descendant survives. Test with a real grandchild: a node fixture that spawns a child node holding a port; after stop the port is free.

**Graceful stop.** Before terminating, deliver Ctrl+C: under a process-wide lock, `FreeConsole`, `AttachConsole(pid)`, `SetConsoleCtrlHandler(None, TRUE)`, `GenerateConsoleCtrlEvent(CTRL_C_EVENT, 0)`, `FreeConsole`, restore the handler; do it off the async executor. Wait up to 10 s for the job to empty, then terminate. A failed attach goes straight to terminate. Report in the activity row whether the stop was graceful. Test with a real node fixture that writes a file in `process.on('SIGINT')`. Confirm the engine survives its own signal.

**Roles.** Add `role: Caddy | App | Connector` to `Spec`, driving `label()` ("The application"), the preflight (only Caddy needs `caddy_ready`), and the NotFound message. Change `path` to `String`. Add `health: Strict2xx | AnyBelow500` (2xx is unchanged for static; a Node app that redirects or returns 404 on `/` is still alive) and `restart: RestartPolicy`. `Never` leaves it stopped with the exit code shown, `OnFailure` does not restart after exit code 0, and crash-loop detection applies to apps.

**Status.** Store health per process key per site and compute the site's status from all of them: `running` only when every process of that site is healthy, `error` with the failing process's message otherwise. With one process (static) the result must equal today's behaviour.

**Loopback by default.** Most apps call `listen(PORT)`, which binds all interfaces and ignores `HOST`. Ship a small preload, compiled in and written to `<data>/run/hostify-loopback.cjs`, that patches `net.Server.prototype.listen` so a TCP listen with no host uses `127.0.0.1`. Leave explicit hosts, pipes and non-TCP handles alone. Pass it with `NODE_OPTIONS=--require "<path>"`, prepended to any `NODE_OPTIONS` the site set. An explicit `0.0.0.0` is honoured but then detected: use `GetExtendedTcpTable` with the job's process IDs, check once after each start, and record a `warn` activity naming the address, also returned by `app_status` as `exposedAddresses`. Test all of it with a real node fixture, including ESM and `listen(port, callback)`.

**Environment for the app.** Allowlist, then the `PATH` from C, `NODE_ENV=production` unless the site set it, the site's resolved variables, then `PORT=<internal>` and `HOST=127.0.0.1`, set last. Redact `secret_values`. Logs go to `<data>/logs/<id>.app.log`. Working directory is the active release plus `workingDir`.

**Start order for a node site.** `start_site`: refuse with a plain sentence unless `activeRelease` (or a `builtRelease` being promoted) is built and equals `trustedRelease`. If the internal port is taken by something else, allocate another and save it. Start the app, wait up to 60 s for `127.0.0.1:<internal><healthPath>` to answer below 500, and if the process has exited say so with its exit code and the last log lines. Then write the Caddy config (E) and start Caddy. Check through Caddy with a real request whose `Host` is not localhost, which must reach the app. Only then report `running`. `stop_site`: Caddy first, then the app, gracefully. Promotion of a `pendingRelease`: stop the old, start the new; if the new one fails, restart the previous release and report that the update failed and the previous version is running. Only then prune.

`site_responds(port)`: look up the site by public port and use its role's health rule. Static is unchanged.

`startup()` and auto-start keep working, starting a site's app before its Caddy. A trusted, built site restarts unattended after an engine restart. A site whose release is not trusted never starts unattended.

`app_status {siteId}`: `{pid, processCount, cpuPercent, memoryBytes, peakMemoryBytes, restarts, lastExitCode, lastExitAt, internalPort, activeRelease, health, exposedAddresses}`. Measure on request using `sysinfo` for the job's process IDs; no background polling. Absent values are absent, never invented. `app_logs {siteId, stream:"app"|"build"|"access", lines}` follows `site_logs`.

## E. Caddy routing (`caddy.rs`)
Add `backend: Backend` to `Site` with `Static{root}` and `Proxy{port}`. `Static` output must stay byte-identical (add a test comparing to a literal). `Proxy` keeps the same marker route and logging, with `handle { reverse_proxy 127.0.0.1:<port> { flush_interval -1 } }`, and keeps the same security header `X-Hostify-Verify`. It also adds a Caddy-only health route `/.well-known/hostify-caddy-ok` responding 200, used as that Caddy worker's health path, so a crashed app does not make Caddy look dead and its own status stays honest.

For non-static sites: write to a temp file in `run/`, run `caddy validate`, atomically rename, and on failure keep the old file and report Caddy's real message. Not zero-downtime; a brief gap for that one site on config change. Say so in `docs/ENGINE.md`.
