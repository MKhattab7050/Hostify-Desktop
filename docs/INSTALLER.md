# Hostify Windows installer

This build is **UNSIGNED**. Windows may show an unknown publisher or SmartScreen warning. No certificate, signing, clean-VM install, reboot/autostart, or installer execution has been verified here. Installer bundling is reserved for the orchestrator, which has network access for the NSIS toolchain.

The NSIS installer uses `currentUser` mode; the default installation needs no administrator rights. On upgrade it stops the previous engine before replacing its executable. It runs `hostify-engine.exe install-task` after installation and starts the engine. The uninstall hook runs the bundled `stop-engine.ps1`, then `remove-task.ps1` (which calls `hostify-engine.exe uninstall-task`) before removing files. An already missing task is treated as removed. The script stops only processes whose executable path equals this installation's engine path; closing the engine's Job Object also terminates its supervised children. A failure aborts uninstall to avoid leaving a running engine or startup task behind. Stopping an already absent engine succeeds. Closing or quitting the UI never calls them.

An unchecked custom uninstall checkbox, **Delete my website data (cannot be undone)**, controls deletion of `%LOCALAPPDATA%\Hostify\sites`. Without explicit opt-in, that directory is kept. The database, logs, and component cache are kept in either case; this checkbox removes only served files and releases. Upgrade uninstall should leave the checkbox unchecked so sites survive upgrades.

Run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/prepare-sidecar.ps1` from the repository root. The configured Tauri `beforeBuildCommand` runs it automatically. It adds `%USERPROFILE%\.cargo\bin` to PATH, builds the engine with `cargo build -p hostify-engine --release --offline`, stages the real executable in `src-tauri/resources/`, regenerates icons locally, and runs `pnpm build`. No installer bundling was run during shell development. `-SkipFrontend` is available when `dist/` already exists. A failed engine build aborts staging/bundling. The resources directory maps to the installation root, putting the engine beside the app executable. The executable is generated and ignored by Git; a shell-only Cargo build can compile without staging it.

The original SVG in `src-tauri/icons/logo.svg` follows the rounded square and line/circle mark in the sidebar. `scripts/generate-icons.ps1` renders the same SVG geometry through Windows System.Drawing, producing PNGs and a multi-resolution ICO without downloads or external packages. Windows is the supported installer target. Native webview drag/drop uses Tauri's event listener permission and the window's `dragDropEnabled`; there is no separate drag/drop command permission in this Tauri version.

Caddy and cloudflared are **not bundled**. When the user requests component setup, the engine downloads the pinned official Caddy v2.11.7 and cloudflared 2026.10.6 assets directly from their release download URLs. Versions, asset filenames, URLs, and SHA-256 hashes are compiled into the single PINNED_COMPONENTS table in `crates/hostify-core/src/components.rs`; Caddy also has its published SHA-512. Every listed hash must match before writing any file. There is no GitHub API call, latest-release lookup, or release-note parsing. To bump a pin: download the intended asset, compute its hashes, verify them against the publisher's checksum list, then update the table's version, filename, URL, and all hashes. After installation, a successful version probe must report the pinned version string; otherwise installation returns an error. Real downloads for this change remain for the orchestrator to verify. Both projects use **Apache-2.0**: Caddy (`https://github.com/caddyserver/caddy/blob/master/LICENSE`) and cloudflared (`https://github.com/cloudflare/cloudflared/blob/master/LICENSE`). Preserve applicable LICENSE/NOTICE files and review third-party dependency notices before redistributing either binary in a future installer. First-run component setup needs internet access; offline tests must use components already available locally.

Run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/smoke.ps1` for the real local HTTP smoke check. It builds offline, refuses an existing per-user engine, starts its own engine with a unique temporary `--data-dir`, imports the sample site, starts it, fetches its loopback preview with curl.exe, then stops the site and the process it created. It never downloads components. Supply `-ComponentsDir <path>` for already provisioned caddy.exe/cloudflared.exe (default `%LOCALAPPDATA%\Hostify\bin`). Missing components or any build, engine, HTTP, or stop failure prints FAIL and returns exit code 1. Temporary artifacts and logs are kept for diagnosis. No mock preview or fabricated PASS is used.
