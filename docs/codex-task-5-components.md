## Observed bug / root cause (verified by the orchestrator)
The installed app's engine uses data dir `%LOCALAPPDATA%\Hostify`; its `bin\` was empty (components had only ever been installed into a different `--data-dir`). The UI correctly says "missing", but: (a) `componentsReady` requires BOTH caddy and cloudflared to run, so a missing cloudflared blocks LOCAL hosting messaging; (b) `start_site` spawns `bin/caddy.exe` with no preflight, yielding a raw "The system cannot find the file specified. (os error 2)"; (c) `ensure_components` only installs when the file is absent, so a zero-byte / corrupt / non-running binary is "present but not ready" and "Install components" silently does nothing forever; (d) nothing reports which data/bin dir the engine uses, and the pipe name is per-user, so the UI can silently talk to an engine started with a different `--data-dir`.

## Required changes
1. **Single source of truth for paths.** One function resolves the data dir (arg `--data-dir` > env `HOSTIFY_DATA_DIR` > `%LOCALAPPDATA%\Hostify`) and derives `bin`, with the exe names `caddy.exe` / `cloudflared.exe` defined once as constants. Make it a pure, unit-testable function (args/env passed in). Service mode must keep using the explicit `--data-dir` captured at `install-service` time (verify; add a test that the service launch arguments carry the same root the task XML does).
2. **Structured component status.** `engine_status` result gains (camelCase, additive; keep `componentsReady`):
   `caddy: {installed:bool, ready:bool, version?:string, path:string, error?:string}`, `cloudflared: {…same…}`, `dataDir:string`, `binDir:string`, `localHostingReady:bool` (= caddy.ready), `componentsReady` stays = caddy.ready && cloudflared.ready (needed to publish). `ready` means the file exists AND `--version`/`version` exits 0 within a timeout. Run the version probes off the async executor (spawn_blocking) with a 5 s timeout and cache results ~2 s (invalidate immediately after any install) so `engine_status` is cheap and always re-detects live — no restart needed after installing.
3. **Install robustness.** `ensure_components` accepts optional params `{"names":["caddy"]}` (default both) and installs a component when it is missing OR not `ready` (zero-byte/corrupt/non-running), replacing atomically (temp file in the same dir, then rename; if the target is locked by a running process return an actionable error). Keep fail-closed checksum verification (Caddy SHA-512 checksums.txt, cloudflared SHA-256 from release notes — already implemented, do not regress). Add a sane maximum download size, ensure a failed/mismatched download leaves no partial file and never replaces an existing working binary, only the single expected entry (`caddy.exe`) is extracted from the Caddy zip (no path from the archive is used), and emit `components-progress` per component. Friendly errors for GitHub rate-limit / offline.
4. **Start preflight.** `start_site` (and restart) must check Caddy is ready BEFORE spawning and return an actionable message such as: `Caddy (the web server) is not installed or can't run. Open the Dashboard and choose "Install components", then start the website again.` — set the site's `statusDetail` to it. It must NOT mention or require cloudflared. Local hosting works with cloudflared absent. `publish_site` preflight requires both and names exactly which is missing. Map any remaining os error 2 on spawn to this same message.
5. **Diagnostics.** `status` CLI subcommand prints data dir, bin dir, and each component's ready/version. Log the resolved data dir at engine start (activity log: "Hostify engine started (data: <dir>)").
6. **Dev vs installed.** Engine already resolves from its data dir only; confirm the Tauri shell's auto-spawned engine (dev: `target/debug`, installed: beside the exe) passes no conflicting dir; add a `dataDir` echo so the shell can log a mismatch. Do not change the autostart task/service design.
7. **Regression tests (all must pass offline):** path resolution precedence; component status matrix (both absent / only caddy / only cloudflared / zero-byte caddy / non-running binary) — use a fake runner trait for probing; `localHostingReady` true with cloudflared absent; zero-byte caddy gets reinstalled by `ensure_components` (mock `Http`); failed checksum leaves existing binary untouched and no temp files; zip with traversal entries only extracts `caddy.exe`; `start_site` with caddy missing returns the actionable message, does not spawn, sets statusDetail; start succeeds with cloudflared missing (can use a small stub exe or the fake-runtime path your existing integration test uses); pipe integration test asserts the new `engine_status` fields. Update/extend existing tests, don't delete them.
